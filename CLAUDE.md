# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

`mahjong-go` is moving out of its bootstrap phase. The repository still
contains the original Connect-Go service skeleton with a sample
`GreetService` used to verify the toolchain wiring, and is now growing the
actual mahjong domain under `internal/` following the DDD architecture
recorded in `docs/design/architecture.md`.

**Read `docs/design/architecture.md` (and the `mahjong-architecture` skill
under `.claude/skills/`) before working on anything under `internal/`** — it
records the bounded contexts (Identity, Matching, Game), the
domain/application/infrastructure layering convention, and key
infrastructure decisions (Identity Platform for auth, backend-relayed
Firestore streaming instead of direct client subscription).

## Tech stack

- **Go 1.25** (module `github.com/leona-art/mahjong-go`)
- **[Connect](https://connectrpc.com/)** (`connectrpc.com/connect`) — RPC framework, serves both gRPC and gRPC-Web/Connect protocols over plain HTTP/2 (h2c, no TLS needed locally)
- **[Buf](https://buf.build/)** (`buf.yaml` / `buf.gen.yaml`, schema `v2`) — proto linting, breaking-change detection, and code generation
- **Protocol Buffers** — schema-first API definitions under `proto/`

## Repository layout

```
proto/<package>/v1/*.proto        # Proto source of truth (buf module root: proto/)
gen/<package>/v1/                 # Generated Go code (protoc-gen-go + protoc-gen-connect-go); DO NOT hand-edit
internal/<context>/domain/        # Entities, value objects, aggregates, domain events, repository interfaces
internal/<context>/application/   # Command/Query use cases (CQS), orchestrates the domain layer
internal/<context>/infrastructure/ # Repository implementations (Firestore, etc.), auth integration
cmd/server/main.go                # Example Connect server (h2c on localhost:8080)
cmd/client/main.go                # Example Connect client calling the server
buf.yaml                          # Buf module config (lint: STANDARD, breaking: FILE)
buf.gen.yaml                      # Buf codegen plugin config
docs/design/architecture.md       # DDD architecture: bounded contexts, layering, infra decisions
go.mod                            # Also pins codegen tools via `tool (...)` directives (Go 1.24+)
```

Proto packages follow a `<service>/v1` versioning convention (e.g.
`greet/v1`), mirrored in both `proto/` and `gen/`. New domains (e.g. a future
`game/v1` or `room/v1`) should follow the same shape.

Bounded contexts under `internal/` (Identity, Matching, Game — see
`docs/design/architecture.md`) each get their own `domain/`, `application/`,
and `infrastructure/` subpackages. The domain layer must not depend on the
other two; the application layer depends only on the domain layer and
reaches infrastructure through interfaces declared in the domain layer.

## Codegen tool management

Buf itself and the protoc plugins are **not** expected to be installed
globally. They are pinned as Go tool dependencies in `go.mod`'s `tool (...)`
block:

```
tool (
	connectrpc.com/connect/cmd/protoc-gen-connect-go
	github.com/bufbuild/buf/cmd/buf
	google.golang.org/protobuf/cmd/protoc-gen-go
)
```

`buf.gen.yaml` invokes them via `go tool <name>` rather than bare binary
names, so `go tool buf generate` works reproducibly from a clean checkout
with no extra global installs. When adding a new codegen plugin, add it as a
tool dependency (`go get -tool <module>/cmd/<plugin>`) and reference it the
same way in `buf.gen.yaml`.

## Common commands

```bash
# Regenerate Go code from proto/ (run after any .proto change)
go tool buf generate

# Lint and breaking-change check for proto files
go tool buf lint
go tool buf breaking --against '.git#branch=main'

# Build everything
go build ./...

# Run the sample server, then the client against it (separate terminals)
go run ./cmd/server
go run ./cmd/client

# Standard Go checks
go vet ./...
go test ./...
```

There is no CI configuration, Makefile, or linter config in the repo yet —
`go vet`, `go build`, and `go tool buf lint` are the closest things to a
verification suite. Run them after making changes.

## Conventions

- **Never hand-edit files under `gen/`.** They are fully regenerated by
  `go tool buf generate`; change the `.proto` source and regenerate instead.
- **Proto-first workflow**: define/modify RPCs and messages in `proto/`,
  regenerate, then implement the handler in Go. Service handlers embed the
  generated `Unimplemented<Service>Handler` struct (see
  `cmd/server/main.go`'s `greetServer`) so partially-implemented services
  still compile.
- **Module path**: proto `go_package` options follow
  `github.com/leona-art/mahjong-go/gen/<package>/<version>;<alias>package`,
  matching the module path in `go.mod`.
- Keep new proto packages under a `<name>/v1` directory and use
  `buf breaking` against `main` before merging changes to an existing
  package's wire format.
- **Test subtest names are Japanese.** The string argument passed to
  `t.Run(...)` must be written in Japanese so failures read clearly for this
  team (e.g. `t.Run("満席の部屋への参加は拒否される", ...)`). Test function
  names (`TestXxx`) stay in English/Go identifier form as usual — only the
  `t.Run` description strings are Japanese. Apply this to every new test,
  not just ones the user calls out explicitly.
